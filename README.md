# AetherKeys — Android keyboard test project (v0.1.0-alpha)

A repository-ready **native Kotlin Android Input Method Editor** for English, Urdu and Sindhi, with **10 bespoke vector theme worlds + 5 original familiar-style ergonomic layouts**, advanced retained clipboard, screenshot sharing, an encrypted login vault with Android Autofill, optional voice typing and Translate & Send.

> **Status: developer alpha, NOT independently compiled or device-certified in this delivery.** The included GitHub Actions workflow is the intended first Android build and test. Treat failures shown in Actions as the authoritative build result; test on real devices before entering valuable credentials. The browser showcase in [`showcase/index.html`](showcase/index.html) is a separate visual demo.

## Build on GitHub without a local Android SDK

1. Create a new **empty** GitHub repository (for example `AetherKeys`).
2. Download the project ZIP from ChatGPT and **extract it first**. Upload the **contents** of `AetherKeys-v0.1.0/` to the root of the repo, including the hidden `.github/workflows` folder. A ZIP uploaded as a single repo file will **not** compile.
3. Commit to `main`, or go to **Actions → Android · Debug APK → Run workflow**.
4. Open the completed workflow run and, under **Artifacts**, download `AetherKeys-v0.1.0-alpha-debug-apk`. Unzip that artifact to obtain `app-debug.apk`.
5. Install on an Android 8.0+ test device and launch AetherKeys. Tap **Enable keyboard**, then **Choose active keyboard**. To use credentials, go to **Secure Login Vault** and separately **enable AetherKeys as Android Autofill provider** in Android Settings.

The workflow installs Android SDK 35, Java 17, Gradle 8.11.1, runs JUnit tests, and builds an unsigned-for-release but **debug-signed test APK** with `:app:assembleDebug`. No secret signing key is required for debug installs. The APK artifact is generated by GitHub, not contained in this source ZIP.

### Android Studio or terminal

Open the repository root as an Android Studio project, let it download Android SDK 35 and Gradle dependencies, then run `:app:assembleDebug`. The repository intentionally uses GitHub's pinned Gradle setup rather than a generated Gradle wrapper JAR. If using a terminal locally, Gradle 8.11.1 must be available in PATH.

## How secure login Autofill works

- In **AetherKeys Settings → Open saved logins**, create a login by entering its **exact target**, a username and password. Use `com.example.app` for a native Android app or `example.com` for a website. A nickname distinguishes multiple accounts.
- In **Settings → Enable AetherKeys as Android Autofill provider**, grant Android's separate Autofill permission.
- In a compatible login form, Android offers a matching saved account. Selecting it invokes system device authentication and then fills the username/password fields.
- The saved account stays encrypted on the device. No password is sent to the developer or to a translation provider. Android Keystore is used to protect data at rest, and passwords are not shown in the Settings list.
- Browser login forms must expose the website origin to the Autofill framework. Never save a password against a generic browser package: a website origin is required to avoid phishing.
- **Manual password paste:** sensitive text saved deliberately as a protected clipboard item can be inserted with `InputConnection.commitText` after authentication, but only where the receiving app permits keyboard input. Some banking apps restrict standard Android input/paste or use proprietary secure fields. Neither the keyboard nor Autofill can bypass those restrictions. **Do not store high-value production banking passwords in this alpha build.**
- **Current limitation:** password saving is manual through Settings; the alpha does **not** yet implement Android's prompt to save a freshly entered password, passkeys, inline Autofill suggestion strip, credential sync, or protected export/import.

## Translation endpoint contract

Offline translation is supported by Google ML Kit between supported languages, with model downloading on first use. For translation involving Sindhi, configure a provider in Settings; it must accept a UTF-8 `POST` HTTPS JSON body:

```json
{"text":"Hello","source":"en","target":"sd"}
```

and return:

```json
{"translatedText":"سلام"}
```

This ZIP includes no translation server and no provider API key. **Only explicitly requested translations** may send text to the configured provider. Never enable remote translation while composing secrets. Translate & Send invokes the current field's IME Send action when exposed by the app; otherwise it inserts translated text and leaves actual sending to the user.

## Clipboard guarantees and limits

- User-enabled history persists across app restarts and stays stored until manually deleted. A pin moves an item to the prominent section without changing the original capture date. Screen shots can be imported using Android's Share menu or file picker.
- On Android 10+, clipboard access is restricted. Default IMEs have broader access than background apps, but **clipboard history is not a blanket system permission**; OS/device/vendor settings can still limit what is captured. Sensitive clipboard content marked by Android is not automatically saved.
- In this alpha, the most recent 100 history entries are visible inside the keyboard, while all retained items remain searchable/manageable from Settings. Encrypted files survive the app process restart but are erased if the app is uninstalled or app data is cleared (Android backups intentionally disabled).
- For an actual password manager launch, strengthen data retention/recovery, corruption handling, unlock session lifetime, biometric/credential lifecycle, rate limiting, clipboard cache scrubbing, audit logging (never plaintext), and a device-based threat model.

## Supported devices and platform roadmap

- **This GitHub repository currently builds only an Android APK** for phones, tablets and foldables. Minimum Android version: 8.0 (API 26); target: 35.
- Native Windows TSF, iOS keyboard extensions, macOS input methods, and Linux IBus/Fcitx require **separate system-integrated frontends**. One APK cannot run as a keyboard on those platforms. Cross-platform design tokens and feature definitions are documented in `docs/PLATFORM-ROADMAP.md`.
- The themes contain their own vector/drawn visual language (no third-party proprietary keyboard UI, logos or assets).

## Known limitations (do not describe as complete Gboard parity)

There is **no production-grade prediction engine, gesture/swipe word recognition, Roman Urdu/Sindhi transliteration model, automatic correction, AI rewrite engine, built-in GIF service, fully offline Sindhi translation, passkeys, credential sync, desktop/iOS port, or independently verified banking-login compatibility** in this alpha. The first goal is to obtain GitHub-compiled test APKs and evaluate the foundation on physical devices before expanding.

## Recommended test plan

1. First run, Android Settings keyboard registration and activation; rotate phone; open SMS, chat and a notes app.
2. English/Urdu/Sindhi typing, symbol page, number row toggles, long presses, key height and floating mode.
3. Switch through all 15 styles; inspect notches, split/foldable screens, small-screen scaling, font and touch target consistency.
4. Enable clipboard and verify text capture, persistence across app restarts, chronological order, pin/unpin and deletion. Import JPEG/PNG screenshots and test share/paste to supported apps.
5. Save **throwaway** test credentials in the vault for a demo Android login form that has Autofill hints. Select Autofill, authenticate and check username/password matching. Verify wrong app/package/site gets no suggestion.
6. Test on-device English/Urdu translation after its ML Kit model download, and attempt Sindhi only with your own configured provider; verify Send falls back to Insert where necessary.
7. Keep verbose bug reports with phone model, Android version, app used, failed action and a screenshot **without passwords**.
